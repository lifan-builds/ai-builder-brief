1. **Google Research Cogentic drops six preprints led by unconditional subexponential integer factoring** — **November 25, 2026 primary repository release (`500` HN points, `370` comments; dedicated factoring thread `125` HN points; Scott Aaronson commentary `1,889` HN points, `1,734` comments)**. Adding six November 25 manuscripts generated by Google's `Cogentic` system (`arXiv:2609.40324`) under Apache-2.0 in `google-research/google-research`, Google Research posted `Unconditional Integer Factorization in Time L_N[1/3, O(1)]`—claiming a zero-error Las Vegas multitape Turing machine factoring every integer `N >= 2` in worst-case expected time `L_N[1/3, 105]` and deterministic workspace `L_N[1/3, 40]`—alongside `Discrete Logarithms in Finite Fields of Fixed Characteristic in Sub-Quasi-Polynomial Time`, a deterministic `algFactor` algorithm in `O(exp(3 (ln N)^(3/4))) = L_N[3/4, o(1)]`, an exact polynomial-time `1/5`-approximate Nash equilibrium algorithm (`MaximinKiteNE`), a polynomial improvement over Lovett's `O(sqrt(r) log r)` log-rank bound (`ε = 5×10^-6`, `C = 2^38`), and unconditional edge reconstruction for graphs with `m >= 1000 n_0`. Security engineers fielding "Factoring in P" panic (`503` HN points on a Reddit rumor thread) should clarify to leadership that `L_N[1/3]` is subexponential—not polynomial—and removes heuristic assumptions from number-field-sieve complexity rather than breaking deployed RSA key sizes today. Major verification gaps remain: all six drops are unrefereed PDFs with zero Lean formalization or reference implementations, and huge asymptotic constants (`105`, `40`, `2^38`) keep them far from practical cryptanalysis. [Google Research Cogentic papers directory](https://github.com/google-research/google-research/tree/master/cogentic_research_papers), [Unconditional Integer Factorization README](https://github.com/google-research/google-research/tree/master/cogentic_research_papers/integer_factorization).

2. **Anthropic migrates its Messages API from Python to Rust using shadow-traffic verifiers** — **November 25, 2026 primary engineering post**. With Messages API volume up `~1,800×` from early 2024 to fall 2026, Anthropic abandoned an incremental Python-to-Rust FFI parser rewrite (which trimmed CPU only `8%–10%` while bouncing every token across the boundary three times) and let Claude—writing `>80%` of merged Anthropic code by May 2026—draft the core Rust request path in about a week. Porting `~700` mocked integration tests proved insufficient: audits uncovered `>100` weakened assertions, and in April a `98%` test pass rate still masked only `~25%` input parity on live traffic (for example, JSON emoji escaping differences). Anthropic turned production itself into a privacy-preserving oracle by running the model once, replaying that exact output to Rust to bypass nondeterminism without double-billing, and logging only structural checkpoint diff fingerprints (step, prompt piece, first-diff byte offset, and byte lengths) without inspecting customer text; automated agent loops consumed those fingerprints to land fixes until public traffic cut over in September 2026, cutting CPU per request `~70%` and median time to first token `~20%` with zero downtime or feature freeze. Platform teams using coding agents for high-stakes rewrites should invest first in production shadow comparators and invariant-locked tests rather than letting agents rewrite both code and mocked suites simultaneously. Measurement boundaries are noted in the charts: CPU figures track one region, memory covers all production, and the `20%` TTFT improvement measures Claude Code traffic over a shorter window where part of the drop occurred before Rust cutover. [Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust).

Formal-verification engineers studying AI-proof bloat (highlighted in November 23's Lean Reservoir audit) now have a concrete artifact showing post-hoc automated refactoring can shrink proof artifacts by two orders of magnitude so reviewers can audit `src/Statements.lean` and replay the kernel on a single workstation. Explicit disclaimers apply: the repository is marked unmaintained and closed to contributions, has passed machine kernel checks only without end-to-end human mathematical review, and ships without a companion prose paper. 5. **vLLM discloses three CVEs for cross-user token leaks, thinking-budget aliasing, and 400 DoS** — **November 26, 2026 (`16:01 UTC`) primary CVE and GHSA advisories**. Three multi-tenant inference vulnerabilities in `vllm` published simultaneously today: `CVE-2026-137477` (`GHSA-v97p-wpxp-px84`, affecting `0.16.0` to `<0.21.0`) leaks stale tokens from previous users into the KV cache when the V1 model runner combines async scheduling with pipeline parallelism because non-last pipeline ranks never write generated tokens to `token_ids_cpu` and reset `num_tokens_no_spec` on each step; `CVE-2026-137475` (`GHSA-fpch-3xrf-7q96`, `0.21.0` to `<0.28.0`) leaves a dangling source entry in the `SWAP` branch of `ThinkingBudgetStateHolder.sync_batch()`, letting a caller setting `thinking_token_budget` bleed reasoning-end token sequences into concurrent co-batched users; and `CVE-2026-137476` (`GHSA-mwgq-9582-w2vf`, `0.3.0` to `<0.30.0`) lets unauthenticated clients amplify CPU and memory use because the OpenAI-compatible server's `RequestValidationError` handler echoes entire offending Pydantic inputs inside HTTP `400` responses (for example on `POST /v1/responses`). Operators running pinned enterprise vLLM branches below `0.30.0` should upgrade immediately—all three bugs are patched by `0.30.0` (`0.21.0`, `0.28.0`, and `0.30.0` respectively)—and review last week's `GHSA-xgh8-qwjh-q853` (`0.32.0rc0–0.34.0`) where `POST /v1/systemone` bypassed `--trust-request-chat-template`. Scope nuance: `CVE-2026-137477` requires both V1 async scheduling and pipeline parallelism on older `<0.21.0` releases, so current `0.30+` deployments are already unaffected by today's trio. [GHSA-v97p-wpxp-px84 (CVE-2026-137477)](https://github.com/vllm-project/vllm/security/advisories/GHSA-v97p-wpxp-px84), [GHSA-mwgq-9582-w2vf (CVE-2026-137476)](https://github.com/vllm-project/vllm/security/advisories/GHSA-mwgq-9582-w2vf), [GHSA-fpch-3xrf-7q96 (CVE-2026-137475)](https://github.com/vllm-project/vllm/security/advisories/GHSA-fpch-3xrf-7q96).

6. **Cloudflare launches one-toggle Search for Agents exposing `/.well-known/search` Markdown indexes** — **November 25, 2026 primary engineering release**. Extending `Markdown for Agents` to site-wide retrieval, Cloudflare put `AI Search` provisioning behind a single zone-level Quick Actions toggle (or API call) available across all plans including Free (with limits). Turning it on crawls and indexes the zone, serves `GET /.well-known/search?q={query}` directly from the customer's own domain returning ranked Markdown chunks rather than synthesized LLM prose, and automatically injects discovery tags (`<meta name="agent:endpoint">`, `agent:instructions`, `agent:method`, `agent:documentation`) into HTML `<head>`—or matching YAML front matter when agents send `Accept: text/markdown`—while respecting existing WAF, Bot Management, and AI Crawl Control rules. Documentation teams and developer-tool vendors behind Cloudflare can flip the toggle to cut redundant agent crawling and deliver grounded Markdown snippets without maintaining a custom vector pipeline, while agent-harness authors should add `agent:endpoint` meta/front-matter discovery before falling back to HTML scraping. Practical limits apply: Free zones face crawl and query quotas, default chunking and caching run without reranking unless explicitly configured in `AI > AI Search`, and discovery fails silently for crawlers that ignore `<meta name="agent:*">` headers. [Introducing Search for Agents](https://blog.cloudflare.com/search-for-agents/).

10. **NVIDIA NOOA study shows model-driven context compaction triples GPT 6.1 accuracy at 32K** — **November 24–26, 2026 primary research & Apache-2.0 harness (`arXiv:2611.34147`, `NVIDIA-NeMo/labs-OO-Agents`)**. Challenging the standard pattern where agent harnesses blindly summarize conversation history once the context window fills, NVIDIA researchers exposed an explicit context-editing API inside `NOOA` (`labs-OO-Agents`) and tested model-driven compaction against harness-triggered compaction on document research (`OfficeQA Pro v2`) and ML engineering across `8K–512K` token budgets. Under tight `32K` budgets, giving the model control nearly tripled `GPT 6.1` accuracy on `OfficeQA Pro v2` (`21% → 56%`), while `Kimi` improved accuracy using up to `41%` fewer input tokens. On the serving side, modifying inference engines to preserve the KV cache of unchanged prompt suffixes after a mid-history compaction edit cut prefill compute by up to `15%` per request with no measurable accuracy loss. Agent-harness engineers should expose explicit scratchpad/compaction tools rather than relying solely on opaque sliding-window summarizers, and inference teams should track KV-cache suffix-reuse patches for long-horizon agent workloads. Behavioral variance is a real caveat: models differed sharply in how aggressively and early they invoked the context API, minor prompt tweaks shifted compaction timing, and KV suffix reuse requires custom inference-engine support not yet standard across hosted APIs. [Letting Models Manage Their Own Context (arXiv:2611.34147)](https://arxiv.org/abs/2611.34147), [NVIDIA-NeMo/labs-OO-Agents repository](https://github.com/NVIDIA-NeMo/labs-OO-Agents).
